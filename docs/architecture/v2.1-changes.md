# Backend Architecture v2.1: changes from v2.0

Changes to [backend-architecture-v2.0.pdf](backend-architecture-v2.0.pdf) after senior developer review
(2026-09-30). Where this file and the PDF disagree, this file wins. Decisions:
[0003 identity service](../decisions/0003-identity-service.md),
[0004 API gateway](../decisions/0004-api-gateway.md),
[0005 admin dashboard](../decisions/0005-admin-dashboard-flutter-web.md).

Unchanged: the Wound Event contract (§5), the device queue (§6), push and pull (§7.1, §7.2), the auth request
and response bodies (§7.3), Kafka (§8), PostgreSQL (§9), the orchestrator and Recommendation Service (§10),
guarantees (§11).

## §2.1 Component view

| Layer | Component | Responsibility |
|-------|-----------|----------------|
| Device | Flutter UI + Drift/SQLite | unchanged |
| **Web** | **Admin dashboard (Flutter Web)** | Facility admins: clinicians, MFA resets, auth audit |
| **Edge** | **API gateway (YARP, .NET 10)** | Single entry point: routing, rate limiting, CORS, edge JWT check |
| **Identity** | **Identity service (ASP.NET Core, .NET 10)** | Login/refresh/logout, MFA, clinician admin; issues RS256 JWTs; publishes OIDC discovery + JWKS |
| Gateway | Sync Gateway | Push/pull, patient alias, figure proxy. **No longer issues tokens**; validates them with the cached JWKS |
| Backbone, Persistence, Orchestration, Recommendation, Store | | unchanged |

## §2.2 The ten steps

Step 1 (Authenticate): the clinician signs in through the API gateway to the **identity service**, which
issues the JWT and refresh token. Step 3 (Accept): the Sync Gateway validates the JWT locally against the
identity service's public keys; no call to the identity service per request.

## §3 Decisions: "Clinician identity" row (replaced)

| Topic | Decision | Why |
|-------|----------|-----|
| Clinician identity | A separate in-house identity service owns login, sessions and clinician admin against the `clinical.clinician*` tables. It signs RS256 JWTs and publishes `/.well-known/openid-configuration` and `jwks.json`; every other service validates tokens locally. | Only one service can mint tokens; others need only a public key. Local validation keeps the request path fast. Still no external identity provider, so the auth story stays concrete and inspectable. |
| Entry point (new) | One API gateway in front of all client HTTP traffic. Kafka stays the service-to-service backbone. | One URL for the app, dashboard and harness; CORS and rate limits in one place. |

## §4 Deployable units (added)

| Unit | Technology | Owner | Consumes | Produces | Scales by |
|------|-----------|-------|----------|----------|-----------|
| API gateway | YARP on ASP.NET Core, .NET 10 | Member 4 | Client HTTP | Proxied HTTP | Stateless replicas |
| Identity service | ASP.NET Core, .NET 10 | Member 4 | HTTP from the API gateway | JWTs, JWKS, `auth_audit` rows | Stateless replicas |
| Admin dashboard | Flutter Web, nginx | Member 4 | API gateway | — | Static files |

The Sync Gateway row no longer lists "JWTs" under Produces or "auth" under Consumes.

## §7.3 Authentication (contract)

Request and response bodies are unchanged for the device. `contracts/auth.schema.json` 1.1 adds an
optional `clientId` on login (`mobile` default, or `admin-dashboard` without a `deviceId`), the error codes
`CLIENT_NOT_ALLOWED`, `DEVICE_NOT_EXPECTED` and `UNKNOWN_CLIENT`, a `client_id` claim on every access
token, and definitions for the discovery document and the JWKS.

## §8.1 Topics: retry consumer group

The retry topics (`wound-events.retry.30s`, `.retry.5m`) are consumed by the orchestrator in its own group,
`orchestrator-retry`, instead of the `orchestrator` group. A retry consumer pauses partitions for up to five
minutes; in a separate group neither that nor its rebalances can stall the main orchestrator consumer.

## §9 Schemas: baseline

A sixth schema, `baseline`, holds the REST baseline's tables (§13.1). It has no unique constraint on `event_id`
on purpose, and nothing on the event-driven path reads or writes it.

## §9.1, §9.4 Database access

- `clinical.clinician_session` gains `client_id` (`mobile` or `admin-dashboard`); `device_id` is nullable
  for `admin-dashboard` sessions only. Additive migration, per §9.2.
- "Only the gateway's role can read `clinical.clinician_credential`" now reads **only the identity
  service's role**. The Sync Gateway's role loses that grant.
- Writers of `audit.auth_audit`: the identity service (was: the gateway).

## §12 Security

- Tokens are signed with RS256. The private signing key is held only by the identity service, in the same
  secrets store as the MFA encryption key. Other services hold only the public keys from the JWKS.
- Tokens issued to the admin dashboard carry no `device_id` and are refused by push and pull.
- The API gateway rate-limits login and refresh, on top of the 5-attempt lockout.

## §13 Evaluation

- The device simulator and the REST baseline both go through the API gateway, so the architecture is
  still the only variable. The latency method notes the extra hop.

## §14 Build order and Appendix A

Deployment adds `api-gateway`, `identity-service` and `admin-dashboard` to Docker Compose; only the API
gateway (and the dashboard) are exposed to the host. Repository additions:

```
backend/apps/api-gateway/         # YARP edge
backend/apps/identity-service/    # auth, MFA, clinician admin, OIDC discovery + JWKS
backend/tests/IdentityService.Tests/
frontend/admin_dashboard/         # Flutter Web
```
